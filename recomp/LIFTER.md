# 리프터 프로토타입 — x86 → C → arm64

`war.exe`의 함수를 C로 변환하고, arm64로 빌드하고, 원본 x86 실행 결과와 자동으로 비교합니다.

## 결과 요약

| 항목 | 결과 |
|---|---|
| 변환 대상 | 게임 영역(`< 0x2F000`)의 리프 함수(다른 함수를 호출하지 않음) 200개 |
| 변환·빌드 | **199개** → C 약 1만 8천 줄 → `clang -O2 -arch arm64` 경고 0 (건너뜀 1개: `rep movsd`) |
| 차등 테스트 | 함수당 150케이스, 총 29,850케이스에서 **불일치 0** |
| 판정 | PASS 191, WEAK 8, FAIL 0 |
| 정상 종료로 검증된 케이스 | 25,550 (나머지 4,300은 양쪽이 같은 사유로 멈춤) |
| 명령어 커버리지 | 평균 95.7%. 100%인 함수 161개, 90% 이상 173개, 50% 미만 3개 |
| ALU 단위 테스트 | 연산 16종 × 폭(8/16/32) = 47조합 × 3,000케이스, 불일치 0 |

**WEAK 8개의 정체**
- **구조화된 입력이 필요한 함수 3개**: `0x1025C`(RLE 스프라이트 블리터), `0x150AC`(연결 리스트 순회), `0x1670C`.
  무작위 입력으로는 정상 종료하지 못합니다. 실제 게임 상태로 검증해야 합니다.
- **단독 함수가 아닌 것 5개**: `0x103D2`, `0x103DD`, `0x103F5`, `0x10402`, `0x1041F`.
  바이트코드 인터프리터 `0x10473`의 opcode 핸들러(테이블 `0x50F90`, `call [ebx+0x50F90]`)입니다.
  종료 핸들러는 인터프리터 함수 안의 `0x10498`로 점프해 `pop ebx`로 **자기 복귀 주소를 버리고** 인터프리터 프레임으로 빠져나갑니다.
  양쪽 모두 `BADRET`으로 멈췄고, 그게 올바른 결과입니다. 이런 비지역 탈출은 함수 단위 변환으로는 표현할 수 없어서,
  인터프리터와 핸들러를 한 C 함수로 묶어 `call`을 `switch` 분기로 바꾸는 처리가 필요합니다.

게임 영역에서 본문을 수집할 수 있는 함수 819개 중 **24개**의 본문이 다른 함수의 주소 범위로 들어갑니다.
대부분 Watcom의 에필로그 공유(꼬리 병합)로 보이고, 그런 경우는 코드를 복제해도 안전합니다.
확인된 비지역 탈출은 위 5개뿐이며, 나머지 19개는 아직 분류하지 않았습니다.

## 구조

```
war.exe ──le.py/disasm.py──▶ tools/lift.py ──▶ build/lifted.c ─┐
                                                               ├─ clang -arch arm64 ─▶ build/liblifted.dylib
runtime/x86.h (메모리·플래그·ALU) + runtime/entry.c ───────────┘
                                                                      │ ctypes
tools/difftest.py:  같은 메모리·레지스터 ─▶ Unicorn(원본 x86) vs liblifted ─▶ 레지스터 8개 + 메모리 2MB 비교
tools/alutest.py:   ALU 헬퍼 vs Unicorn 명령어 단위 비교 (결과 + 정의된 플래그)
```

### 변환 방식 (`tools/lift.py`)
- 함수마다 `void f_<주소>(Cpu *c)`. 레지스터 8개는 C 지역 변수, 플래그(CF/ZF/SF/OF/PF)는 지역 구조체입니다.
  clang이 쓰이지 않는 플래그 계산을 지웁니다.
- 함수 안의 분기는 라벨과 `goto`로, `call`은 리프팅된 함수 직접 호출로, 다른 함수로의 `jmp`는 꼬리 호출로 바꿉니다.
- 게스트 메모리는 flat 바이트 배열이고 게스트 주소가 곧 오프셋입니다(DOS/4GW의 base 0 셀렉터와 같음).
- **지원하지 않는 명령어가 하나라도 있으면 함수 전체를 건너뛰고** 이유를 출력합니다. 부분 변환은 없습니다.
- 안전 장치(런타임에서 위반 시 정지):
  - 범위 밖 메모리 접근 → `FAULT`
  - 코드 오브젝트에 쓰기 → `FAULT` (게임 코드는 자기 코드를 고치지 않음. CRT/AIL의 코드 내 쓰기는 HLE 대상)
  - `ret`이 호출자가 넣은 복귀 주소가 아닌 값을 꺼냄 → `BADRET` (스택 오염을 조용히 넘기지 않음)
  - 역방향 분기 횟수가 예산 초과 → `BUDGET` (무한 루프 방지)
  - 0으로 나누기·몫 넘침 → `DIVIDE`
- 리프팅 시 거부: `call` 직후 호출자가 피호출자의 플래그를 읽는 함수
  (플래그가 지역 변수라 함수 경계를 넘지 못하기 때문).

### 차등 테스트 (`tools/difftest.py`)
- **기준(오라클)**: Unicorn 2.1.4로 원본 x86 코드를 같은 주소에서 실행합니다.
- **입력**: war.exe 이미지(재배치 적용) + 스크래치 영역 무작위 바이트 + 무작위 레지스터.
  첫 실행에서 함수가 읽는 전역 변수 주소를 수집하고, 이후 케이스에서 그 주소에
  작은 정수·경계값·무작위 값·유효 포인터를 넣습니다("읽기 집합 퍼징").
- **판정**: 양쪽 정지 사유가 같고, 정상 종료면 레지스터 8개와 메모리 2MB가 바이트 단위로 같아야 합니다.
  양쪽이 같은 사유로 멈춘 케이스는 "둘 다 정지"로 따로 셉니다(일치하지만 의미 검증으로는 약함).
- 정지 조건을 양쪽에서 같은 기준으로 맞췄습니다. 역방향 분기 한도, 코드 쓰기 금지, 본문 밖 실행(= 잘못된 복귀)이 그 기준입니다.
- `PASS` = 불일치 0 + 정상 종료 케이스 ≥1, `WEAK` = 불일치 0이지만 정상 종료 케이스 없음, `FAIL` = 불일치 있음.

### 테스트가 실제로 버그를 잡는지 (변이 시험)
런타임 헤더와 생성 C에 대표적인 실수 8가지를 하나씩 심어 확인했습니다.

| 심은 버그 | 함수 차등 테스트 | ALU 테스트 |
|---|---|---|
| sub의 캐리 `<` → `<=` | 검출 (3개 함수) | 검출 (sub/sbb) |
| jl 조건 반전 | 검출 (2개 함수) | — |
| movsx를 movzx로 | 검출 (1개 함수) | — |
| AH 쓰기 마스크 오류 | 검출 (1개 함수) | — |
| sar의 캐리 위치 | 미검출 | 검출 (sar) |
| inc가 CF를 지움 | 미검출 | 검출 (inc) |
| add 오버플로 0 고정 | 미검출 | 검출 (add/adc) |
| 패리티 반전 | 미검출 | 검출 (전 산술 연산) |

함수 테스트는 반환 시점의 플래그를 비교하지 않기 때문에, 해당 플래그를 읽지 않는 함수에서는
플래그 버그가 드러나지 않습니다. ALU 테스트가 그 빈틈을 메웁니다. 두 테스트를 합치면 8개 모두 검출됩니다.

## 한계

- **반환 시점 플래그는 비교하지 않습니다.** 대신 리프터가 "call 뒤 플래그 읽기"를 거부하므로 플래그가 함수 경계를 넘는 코드는 변환되지 않습니다.
- **무작위 입력의 한계**: RLE 블리터(`0x1025C`)처럼 구조를 갖춘 데이터가 필요한 함수는 정상 종료 케이스를 거의 만들지 못합니다(WEAK).
  실제 게임 상태를 입력으로 써야 합니다(아래 DOSBox-X 계획).
- 미지원: `rep` 문자열 명령, 16비트 push/pop, 8/16비트 나눗셈, x87, 세그먼트 오버라이드, 간접 call/jmp(switch 포함)
  — 이번 범위는 **게임 영역의 리프 함수**입니다.
- Unicorn도 에뮬레이터이므로 "실제 CPU와 같다"가 아니라 "Unicorn(QEMU 기반)과 같다"를 보장합니다.

## DOSBox-X 상태 캡처 (다음 단계)

DOSBox-X 2026.10.01(Homebrew)을 설치했고, 디버거 명령(`BP`, `EV`, `MEMDUMPBIN`, `LOGL`)과 `-break-start`가 있음을 확인했습니다.
아직 캡처는 하지 않았습니다. 계획은 이렇습니다:

1. CD 파일과 풀어 둔 `war.exe`로 게임 폴더를 만들어 DOSBox-X에서 실행합니다(사운드 없음).
2. 디버거 UI는 터미널 기반이므로 tmux 안에서 실행하고 `send-keys`로 명령을 자동 입력합니다.
3. DOS/4GW는 LE 오브젝트를 기본 주소(0x10000/0x50000)가 아닌 곳에 올립니다.
   그래서 메모리 덤프에서 코드 바이트를 찾아 **실제 로드 주소**를 구하고, `le.py`가 그 주소로 재배치한 이미지로 **다시 리프팅**합니다.
   캡처한 메모리 안의 포인터를 기본 주소로 되돌리는 것은 불가능하기 때문입니다.
4. 대상 함수 진입점과 복귀 지점에 `BP`를 걸고, 레지스터와 메모리를 덤프해 (입력, 기대 출력) 쌍을 만듭니다.
   이 쌍은 `difftest.py`의 입력으로도 쓰고, DOSBox 자체의 실행 결과와 직접 비교하는 데도 씁니다.

## 실행

```bash
python3 recomp/tools/lift.py recomp/build/lifted.c --all-leaf
clang -O2 -arch arm64 -shared -fPIC -Irecomp/runtime recomp/build/lifted.c recomp/runtime/entry.c -o recomp/build/liblifted.dylib
clang -O2 -arch arm64 -shared -fPIC recomp/runtime/alu_test.c -o recomp/build/libalu.dylib
python3 recomp/tools/alutest.py
python3 recomp/tools/difftest.py --cases 150        # 특정 함수만: ... 139dc 2b21c
```

필요한 것: Python 패키지 `capstone`, `unicorn`; Xcode clang.
