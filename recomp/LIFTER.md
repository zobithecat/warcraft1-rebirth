# 리프터 프로토타입 — x86 → C → arm64

`war.exe`의 함수를 C로 변환하고, arm64로 빌드하고, 원본 x86 실행 결과와 자동으로 비교합니다.

## 결과 요약

| 항목 | 결과 |
|---|---|
| 변환 대상 | 게임 영역(`< 0x2F000`)의 리프 함수(다른 함수를 호출하지 않음) 200개 |
| 변환·빌드 | **199개** → C 약 1만 8천 줄 → `clang -O2 -arch arm64` 경고 0 (건너뜀 1개: `rep movsd`) |
| 차등 테스트 | 함수당 150케이스, 총 29,850케이스에서 **불일치 0** |
| 판정 | PASS 191, WEAK 8, FAIL 0 |
| 정상 종료로 검증된 케이스 | 25,550 (나머지 4,300은 양쪽이 같은 사유로 멈춤) |
| 명령어 커버리지 | 평균 95.7%. 100%인 함수 161개, 90% 이상 173개, 50% 미만 3개 |
| ALU 단위 테스트 | 연산 16종 × 폭(8/16/32) = 47조합 × 3,000케이스, 불일치 0 |

**WEAK 8개의 정체**
- **구조화된 입력이 필요한 함수 3개**: `0x1025C`(RLE 스프라이트 블리터), `0x150AC`(연결 리스트 순회), `0x1670C`.
  무작위 입력으로는 정상 종료하지 못합니다. → `0x1025C`와 `0x1670C`는 아래 DOSBox-X 실측 상태로 검증했습니다.
  `0x150AC`는 아직 미검증입니다.
- **단독 함수가 아닌 것 5개**: `0x103D2`, `0x103DD`, `0x103F5`, `0x10402`, `0x1041F`.
  바이트코드 인터프리터 `0x10473`의 opcode 핸들러(테이블 `0x50F90`, `call [ebx+0x50F90]`)입니다.
  종료 핸들러는 인터프리터 함수 안의 `0x10498`로 점프해 `pop ebx`로 **자기 복귀 주소를 버리고** 인터프리터 프레임으로 빠져나갑니다.
  양쪽 모두 `BADRET`으로 멈췄고, 그게 올바른 결과입니다. 이런 비지역 탈출은 함수 단위 변환으로는 표현할 수 없어서,
  인터프리터와 핸들러를 한 C 함수로 묶어 `call`을 `switch` 분기로 바꾸는 처리가 필요합니다.

게임 영역에서 본문을 수집할 수 있는 함수 819개 중 **24개**의 본문이 다른 함수의 주소 범위로 들어갑니다.
대부분 Watcom의 에필로그 공유(꼬리 병합)로 보이고, 그런 경우는 코드를 복제해도 안전합니다.
확인된 비지역 탈출은 위 5개뿐이며, 나머지 19개는 아직 분류하지 않았습니다.

## 구조

```
war.exe ──le.py/disasm.py──▶ tools/lift.py ──▶ build/lifted.c ─┐
                                                               ├─ clang -arch arm64 ─▶ build/liblifted.dylib
runtime/x86.h (메모리·플래그·ALU) + runtime/entry.c ───────────┘
                                                                      │ ctypes
tools/difftest.py:  같은 메모리·레지스터 ─▶ Unicorn(원본 x86) vs liblifted ─▶ 레지스터 8개 + 메모리 2MB 비교
tools/alutest.py:   ALU 헬퍼 vs Unicorn 명령어 단위 비교 (결과 + 정의된 플래그)
```

### 변환 방식 (`tools/lift.py`)
- 함수마다 `void f_<주소>(Cpu *c)`. 레지스터 8개는 C 지역 변수, 플래그(CF/ZF/SF/OF/PF)는 지역 구조체입니다.
  clang이 쓰이지 않는 플래그 계산을 지웁니다.
- 함수 안의 분기는 라벨과 `goto`로, `call`은 리프팅된 함수 직접 호출로, 다른 함수로의 `jmp`는 꼬리 호출로 바꿉니다.
- 게스트 메모리는 flat 바이트 배열이고 게스트 주소가 곧 오프셋입니다(DOS/4GW의 base 0 셀렉터와 같음).
- **지원하지 않는 명령어가 하나라도 있으면 함수 전체를 건너뛰고** 이유를 출력합니다. 부분 변환은 없습니다.
- 안전 장치(런타임에서 위반 시 정지):
  - 범위 밖 메모리 접근 → `FAULT`
  - 코드 오브젝트에 쓰기 → `FAULT` (게임 코드는 자기 코드를 고치지 않음. CRT/AIL의 코드 내 쓰기는 HLE 대상)
  - `ret`이 호출자가 넣은 복귀 주소가 아닌 값을 꺼냄 → `BADRET` (스택 오염을 조용히 넘기지 않음)
  - 역방향 분기 횟수가 예산 초과 → `BUDGET` (무한 루프 방지)
  - 0으로 나누기·몫 넘침 → `DIVIDE`
- 리프팅 시 거부: `call` 직후 호출자가 피호출자의 플래그를 읽는 함수
  (플래그가 지역 변수라 함수 경계를 넘지 못하기 때문).

### 차등 테스트 (`tools/difftest.py`)
- **기준(오라클)**: Unicorn 2.1.4로 원본 x86 코드를 같은 주소에서 실행합니다.
- **입력**: war.exe 이미지(재배치 적용) + 스크래치 영역 무작위 바이트 + 무작위 레지스터.
  첫 실행에서 함수가 읽는 전역 변수 주소를 수집하고, 이후 케이스에서 그 주소에
  작은 정수·경계값·무작위 값·유효 포인터를 넣습니다("읽기 집합 퍼징").
- **판정**: 양쪽 정지 사유가 같고, 정상 종료면 레지스터 8개와 메모리 2MB가 바이트 단위로 같아야 합니다.
  양쪽이 같은 사유로 멈춘 케이스는 "둘 다 정지"로 따로 셉니다(일치하지만 의미 검증으로는 약함).
- 정지 조건을 양쪽에서 같은 기준으로 맞췄습니다. 역방향 분기 한도, 코드 쓰기 금지, 본문 밖 실행(= 잘못된 복귀)이 그 기준입니다.
- `PASS` = 불일치 0 + 정상 종료 케이스 ≥1, `WEAK` = 불일치 0이지만 정상 종료 케이스 없음, `FAIL` = 불일치 있음.

### 테스트가 실제로 버그를 잡는지 (변이 시험)
런타임 헤더와 생성 C에 대표적인 실수 8가지를 하나씩 심어 확인했습니다.

| 심은 버그 | 함수 차등 테스트 | ALU 테스트 |
|---|---|---|
| sub의 캐리 `<` → `<=` | 검출 (3개 함수) | 검출 (sub/sbb) |
| jl 조건 반전 | 검출 (2개 함수) | — |
| movsx를 movzx로 | 검출 (1개 함수) | — |
| AH 쓰기 마스크 오류 | 검출 (1개 함수) | — |
| sar의 캐리 위치 | 미검출 | 검출 (sar) |
| inc가 CF를 지움 | 미검출 | 검출 (inc) |
| add 오버플로 0 고정 | 미검출 | 검출 (add/adc) |
| 패리티 반전 | 미검출 | 검출 (전 산술 연산) |

함수 테스트는 반환 시점의 플래그를 비교하지 않기 때문에, 해당 플래그를 읽지 않는 함수에서는
플래그 버그가 드러나지 않습니다. ALU 테스트가 그 빈틈을 메웁니다. 두 테스트를 합치면 8개 모두 검출됩니다.

## 한계

- **반환 시점 플래그는 비교하지 않습니다.** 대신 리프터가 "call 뒤 플래그 읽기"를 거부하므로 플래그가 함수 경계를 넘는 코드는 변환되지 않습니다.
- **무작위 입력의 한계**: RLE 블리터(`0x1025C`)처럼 구조를 갖춘 데이터가 필요한 함수는 정상 종료 케이스를 거의 만들지 못합니다(WEAK).
  그래서 아래 DOSBox-X 캡처로 실제 게임 상태에서 검증합니다.
- 미지원: `rep` 문자열 명령, 16비트 push/pop, 8/16비트 나눗셈, x87, 세그먼트 오버라이드, 간접 call/jmp(switch 포함)
  — 이번 범위는 **게임 영역의 리프 함수**입니다.
- Unicorn도 에뮬레이터이므로 "실제 CPU와 같다"가 아니라 "Unicorn(QEMU 기반)과 같다"를 보장합니다.

## DOSBox-X 실제 상태 캡처

무작위 입력이 닿지 못하는 함수를 **실제 게임이 실행 중일 때의 상태**로 검증합니다.

### 동작 (`tools/capture.py`, `tools/dbx.py`)
1. CD 파일과 풀어 둔 실행 파일로 게임 폴더를 만들고(INSTALL.EXE가 하는 일과 같음),
   `capture/dosbox.conf.in`으로 DOSBox-X를 **사운드 없이, SDL dummy 드라이버로 창 없이** 실행합니다.
2. 디버거는 터미널(curses) UI라서 **tmux 세션 안에서 실행**하고 `send-keys`로 명령을 입력하고 `capture-pane`으로 화면을 읽습니다.
   (Mac의 DOSBox-X는 stdout이 TTY가 아니면 디버거를 끕니다. 파이프로 감싸면 안 됩니다.)
3. **실제 로드 주소 찾기**: `BPINT 21 FF 00`으로 멈춥니다. DOS/4GW 자신도 같은 호출을 수백 번 하므로,
   32비트 모드이고 `EDX=0078h`인 정지(war.exe 스타트업 `0x33502`)까지 진행합니다. 그 EIP에서 코드 델타를,
   덤프에서 읽은 재배치된 포인터로 데이터 델타를 구합니다.
   실측: **코드 `0x1CB000`, 데이터 `0x1FD000`** (기본 주소 `0x10000`/`0x50000` 대비 `+0x1BB000`/`+0x1AD000`).
   이 베이스로 `le.py`가 재배치한 코드 오브젝트는 **DOSBox 메모리와 200,859바이트 전부(fixup 포함) 일치**합니다.
4. **재배치 리프팅**: 캡처한 메모리 안의 포인터를 기본 주소로 되돌릴 수는 없으므로, 반대로
   `lift.py --bases 1=0x1CB000,2=0x1FD000`으로 실제 레이아웃에 맞춰 다시 변환합니다.
5. **캡처**: 대상 함수마다 진입점에 `BP`를 겁니다. 진입하면 레지스터와 메모리 16MB를 덤프하고, 스택의 복귀 주소에 `BP`를 걸어
   복귀하면 다시 덤프합니다. BP는 처음 한 번만 걸고 번호를 직접 계산해 지웁니다
   (DOSBox-X는 최신 BP가 00번이고 삭제 시 번호를 다시 매김).

### 재생 (`tools/replay.py`)
같은 진입 상태를 **Unicorn**과 **리프팅된 arm64 코드**에서 실행하고, **DOSBox가 실제로 남긴 복귀 상태**와 세 방향으로 비교합니다.
- 레지스터 8개: 세 쪽이 같아야 합니다.
- 메모리: Unicorn과 리프팅 코드의 16MB가 같아야 하고, 함수가 쓴 모든 바이트가 DOSBox 결과와 같아야 합니다.
- DOSBox에서만 바뀐 바이트(함수가 쓰지 않음)는 실패가 아니라 따로 보고합니다. 두 덤프 사이에도 실제 기계는
  인터럽트를 처리하기 때문입니다. 예: `1025c_0`에서 BIOS 틱 카운터 `0x46C`.

### 결과

| 항목 | 결과 |
|---|---|
| 로드 주소 | 코드 `0x1CB000`, 데이터 `0x1FD000` (`CS=0150`, `DS=0158`) — 실행할 때마다 같음 |
| 캡처 범위 | 리프팅된 199개 전부에 BP. 입력 없이 진행되는 인트로·메뉴 구간에서 **15개 함수가 실행됨** |
| 캡처 | **23건**, 전부 정상 복귀(ESP가 진입 시 +4) |
| 재생 | **23/23 일치** (DOSBox 실측 = Unicorn = 리프팅된 arm64) |
| WEAK였던 함수 | `0x1025C` RLE 블리터 2건, `0x1670C` 2건 → **실제 상태로 검증됨**. `0x150AC`는 이 구간에서 실행되지 않음 |

- 함수가 쓴 바이트 수는 DOSBox에서 실제로 바뀐 바이트 수와 일치합니다(블리터는 최대 46,091바이트).
  예외는 `1025c_1` 하나입니다. 블리터가 도는 사이 타이머 인터럽트로 BIOS 틱(`0x46C`) 등 160바이트가 바뀌었고,
  재생기가 이를 "함수와 무관한 변화"로 따로 분리했습니다.
- 변이 시험(런타임 주소용 생성 코드에 버그 4종): movsx→movzx 5건, js 조건 반전 3건, sub 캐리 1건,
  특정 값에서 1바이트 어긋나게 쓰기 3건 실패 → **4종 모두 검출**(초기 11건 캡처 기준).
- 실측으로 정적 분석도 확인됐습니다. 모드 13h 설정 시점에 코드 오브젝트에서 원본과 다른 바이트는
  `0x33438~0x33439` 2바이트뿐이고, 디스어셈블러가 "코드 안 쓰기 대상"으로 찾아 둔 CRT의 DS 저장 변수입니다.

### 겪은 문제와 결정
- 처음에는 war.exe의 `int 21h AX=FF00h`(DOS/4GW 확인)에서 멈춰 주소를 구했습니다. 하지만 DOS/4GW 자신이 같은 호출을
  수백 번 해서 매번 몇 분씩 걸렸습니다. 그래서 **war.exe만 호출하는 `int 10h AX=0013h`**(`0x31281`, `platform_map`이 찾음)로 바꿨습니다.
- **DOSBox-X의 BP 번호는 16진수**(`09`, `0A`, …)이고 `BPDEL`도 16진수로 받습니다. 처음에 10진수로 다뤄서 엉뚱한 BP가 지워졌습니다.
  지금은 BP를 바꿀 때마다 `BPLIST`를 읽어 주소로 번호를 찾고, 대상은 목록이 한 화면에 들어가도록 25개씩 배치로 나눕니다.
- 디버거는 출력이 TTY가 아니면 꺼지므로 DOSBox-X를 tmux에 직접 띄웁니다(`tee` 등으로 감싸면 안 됨).

### 한계와 다음 단계
- 입력 없이는 인트로·메뉴만 지나가므로 **실제 플레이 중에만 실행되는 함수(예: `0x150AC`)는 아직 캡처하지 못했습니다.**
  DOSBox-X의 `AUTOTYPE`나 키 입력 주입으로 메뉴를 넘겨 게임을 시작하면 범위를 넓힐 수 있습니다.
- 캡처는 진입 시점과 복귀 시점 사이 DOSBox의 모든 변화를 함수 탓으로 보지 않도록 분리하지만,
  ISR이 **함수가 쓴 바로 그 주소**를 같은 구간에 덮어쓰면 오탐(FAIL)이 날 수 있습니다(지금까지는 없음).

## 네이티브 뷰어 (`build/blitview`)

리프팅된 게임 코드를 **Python 없이** 실행하는 arm64 실행 파일입니다. DOSBox-X에서 캡처한 인트로 키 프레임들을
원본 게임의 RLE 블리터(`0x1025C`, 리프팅 후 네이티브)로 직접 디코딩해 SDL2 창에 재생하고,
프레임마다 DOSBox-X 결과와 같은지 창 제목에 표시합니다.

```bash
cd recomp
make            # build/blitview (리프팅된 C 생성 + clang arm64 링크)
make frames     # work/frames 캡처 → work/demo/intro.wcf (프레임 묶음)
make run        # 창 띄우기: Space 일시정지, ←/→ 한 프레임씩, Esc 종료
make check      # 창 없이 모든 프레임 디코딩·검증·시간 측정
```

- 프레임 묶음은 `tools/capture.py --capdir work/frames --per-func 40 1025c`로 캡처한 뒤 `make frames`로 만듭니다.
  `pack_frames.py`가 Unicorn 메모리 훅으로 블리터가 실제로 읽고 쓰는 바이트만 골라 담으므로, 프레임당 약 130KB입니다(캡처 원본은 32MB).
- 뷰어는 프레임마다 게스트 메모리(원본 RLE, 호출 전 버퍼, 스택의 복귀 주소)를 다시 만들고, 리프팅된 함수를 호출한 뒤
  버퍼와 레지스터를 DOSBox-X 결과와 비교합니다.
- 결과: 인트로 키 프레임 **11개**(320×144 장면 10개, 320×200 화면 1개)가 모두 **DOSBox-X와 픽셀·레지스터까지 동일**,
  네이티브 디코딩은 프레임당 평균 약 50µs입니다(`make check`).
- 팔레트는 동영상의 팔레트 청크(`0x58C30`)를 호출 **후** 덤프에서 읽습니다. 호출 시점의 DAC 사본(`0x61F80`)에는
  아직 이전 장면의 팔레트가 들어 있어 장면이 바뀌는 프레임의 색이 틀립니다.
- 필요한 것: SDL2(`brew install sdl2`). 실행 파일은 SDL2와 시스템 라이브러리에만 링크됩니다.
- 게임 데이터에서 나온 파일(`build/lifted_rt.c`, `work/`)은 저장소에 넣지 않습니다.
